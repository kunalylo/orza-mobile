## Native issues (not changed — Kotlin module is read-only here)

- Process dead (`am kill`): the 15:55:00 alarm started the process at 15:55:00.16 ("Start proc … for broadcast AlarmReceiver") but the notification + ringtone came at 15:55:05.9 — ≈ 6 s of app/RN start-up (debug dev-client build, emulator) before `AlarmReceiver` runs. Probably much shorter in a release build; worth measuring on a real phone (an alarm receiver ideally doesn't wait for the React host).
- After `adb reboot` Android delivered BOOT_COMPLETED to `BootReceiver` ≈ 65 s after `sys.boot_completed` (system broadcast queue, not the app); an alarm due in that first minute would show as "missed" (by design, MISSED_GRACE). No action needed — noted for expectations.
- Nothing else: channel `orza_alarms` (alarm usage, own sound, vibration, INSISTENT, category alarm, full-screen intent), grouped BigPicture, actions with the app dead, snooze re-ring keys, silencer, reboot reschedule and shown/actions stores all behaved.

## Backend issues

- `POST /api/meds/doses` can't take the time a dose action was pressed (`acted_at`) or an absolute `snooze_until`, and `snooze_minutes` must be 5–60: an action recorded offline / with the app asleep gets the server's receipt time as `acted_at`, and a late snooze with < 5 min left is pushed to +5 min (B4 workaround in the app). Suggest accepting an optional client `acted_at` (clamped to the last few hours).
